# 前哨站自瞄排查记录

2026-11-17

这篇记的是这几天排查前哨站打不中的过程，包括走过的弯路，
重点是后面那几条结论，前面的坑别再踩一遍。

## 一 现象

仿真里开前哨站，能看到三块红板在转，检测器也出结果，但：

- 三个黄框画不到板上，整体偏
- 黄框围着转的那个圆心会动
- 跟踪断断续续，tracking 大部分时间是 false
- 没锁定的时候云台照样开火，还会往反方向扭
- 命中率长期在 0 到 20 之间

## 二 先把距离量清楚

第一件事是确认"以为的距离"和"实际距离"差多少。

用 TF 查了现场几何：

| 对象 | 世界坐标 |
|---|---|
| 云台底座 | -5.00, 0.00, 0.65 |
| 相机 | -4.83, 0.00, 1.04 |
| 前哨站旋转中心 | -1.00, 0.00, 0.00 |

板半径 0.2765 米，三块板高度 1.114 / 1.216 / 1.318 米。板到相机的真实距离在
3.6 到 4.1 米之间。

而检测器报出来的中位数是 **2.4 米**，只有真值的六成。

## 三 距离为什么会错

PnP 算距离只有一个依据：它以为那两条灯条之间的物理宽度是 135 毫米。

如果配对抓到的不是同一块板的左右两条边，实际宽度不是 135 毫米，解出来的距离就
按比例偏掉。我们测到 2.4 对 4.0，比值 0.6，等于把一段只有 81 毫米宽的东西当成
了 135 毫米。

后来把每个被接受的配对的数据打出来，真假差得很明显：

| | 数量 | center_distance 中位 | 灯条像素长度中位 |
|---|---|---|---|
| 距离正确 3.4 到 4.6 米 | 163 | 0.38 | 24.7 px |
| 距离偏小 小于 3.0 米 | 117 | 0.43 | 34.8 px |

假配对抓到的是被连在一起的大灯条，物理尺寸比真灯条长六成，所以解出来更近。

## 四 几个改对了的地方

这几条是确定有效、跟运气无关的：

| 改动 | 效果 |
|---|---|
| 半径写死 0.2765，状态从 11 维降到 10 维 | 半径不再塌，实测恒为 0.2765 |
| 逐板高度偏移进 Target 消息，新增 dz_list 字段 | 三块框终于有高度差，实测 0 / 0.102 / 0.204 |
| 强制转速，符号做成参数 | v_yaw 恒定，不再飘 |
| 更新门限分两段，检测态 1.0 米，跟踪态 0.1 米 | 先锁上再收紧 |
| 状态机容忍连丢 50 帧 | 不再丢一帧就重启 |
| 前哨站未锁定时不下发角度、不发开火 | 没目标不再乱开火 |

半径写死这条是参考了别的战队的做法。单看一块板时半径根本不可观，交给滤波去估只会
一路塌到几毫米，圆心也跟着被带偏。半径本来是机械尺寸，写死更稳。

## 五 数据驱动定阈值

把宽窗口下每个被接受配对的 center_distance 和它最终解出的距离一起打出来，按比值
分桶统计正确率：

| cd 区间 | 样本 | 正确 | 正确率 |
|---|---|---|---|
| 0.2 到 0.5 | 239 | 95 | 40% |
| 0.5 到 0.7 | 137 | 15 | 11% |
| 0.6 到 1.1 | 375 | 2 | 1% |
| 大于 0.8 | 130 | 0 | 0% |

窗口从 0.2 到 2.8 收到 0.2 到 0.5，丢掉七成观测，但留下的正确率从 14% 提到 40%。
改完之后圆心 x 从 2.7 变成 3.78 到 3.96，真值 4.0。

## 六 走过的弯路

这几条记下来，避免重复。

**一 同时跑了十二个 gimbal_controller**

每次重启只杀了 launch 父进程，子节点全活着堆着。最夸张的时候有 12 个控制器、
12 个 /gimbal/fire 发布者同时在线。后果是云台被十二路指令抢着写、发射信号有十一
路是不受新逻辑管的旧版本。

那段时间所有 A/B 数据都是污染的，包括一次测得 49% 命中率，重跑就没了。

以后每次测之前先确认 `ros2 topic info` 里发布者只有一个。

**二 一开始把 center_distance 的理论值算错了**

按网格算出来 2.15，据此把窗口卡在 1.2 到 2.4，结果检测直接归零。真实值在 0.39
附近。那个 2.15 是把灯条长度的定义搞反了算出来的。

**三 center_distance 不是一个和视角无关的量**

这一点最坑。板正对相机时比值约 0.39，侧过来会往 0 掉。所以固定一个窄窗口，板转到
某些角度就配对失败，跟踪就断。窄窗口只能在特定角度有效。

## 七 当前状态

清理干净、云台正对、只跑一套的情况下测的：

| 指标 | 数值 | 说明 |
|---|---|---|
| 检测是否正确 | 准 | 调试图里绿叉落在板中央 |
| 圆心 x | 3.78 到 3.96 | 真值 4.0，已经对 |
| 半径 | 0.2765 | 写死，对 |
| dz_list | 0 / 0.102 / 0.204 | 和真值一致 |
| yaw 相位残差 | 30 到 50 度 | 不对 |
| tracking | 70% 到 86% | 窗口放宽时高 |
| 命中率 | 17% | 之前是 0 |

## 八 结论：问题在 yaw 相位

黄框不是检测器画的，是 EKF 状态算出来的，公式是圆心加上半径在 yaw 加 120 度
方向的投影。

现在圆心对了、半径对了、高度也对了，唯一错的是 yaw 相位，残差 30 到 50 度。
三个框因此整体转过一个角度，落到两块真板中间，看起来就是套不住。

相位对不上有两个原因：

一是板号靠高度差判。三块板高度只差 0.102 米，四米外 PnP 的 z 误差经常超过这个
间隔，判错一次相位就差 120 度。

二是配对窗口固定，板转到某些角度配对就失败，观测断断续续，相位没有足够约束。

## 九 待办

1 相位约束改成不依赖板号。圆心和半径都准了，可以直接用观测到的板的实际位置反推
相位，绕开板号判定。

2 配对窗口改成随视角自适应，别用固定窄窗口。

3 修完之后重测命中率，目标是稳定超过五成。

4 上面这些改动目前都还没提交，先提交存档再继续。
